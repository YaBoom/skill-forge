Turn a finished workflow into a tested, publish-ready Agent Skill.

Most skill tools start from a blank page and ask you to describe the workflow. Skill Forge starts from what you already ran — git history, terminal output, project files — and refuses to write a step it cannot trace to evidence.

The difference

Described from memory
1. Check whether the canonical and
   mirror directories match
2. If they differ, copy canonical
   into the mirror
3. Verify the sync succeeded

No command. No exit condition. Every step has to be improvised at runtime.

Harvested from a real run
$ python scripts/sync_mirror.py --check
drift: SKILL.md
$ python scripts/sync_mirror.py
synced plugins/skill-forge/... -> skills/...
$ python scripts/sync_mirror.py --check
mirror is in sync

Five steps, each with a command and a machine-checkable exit condition.

A skill can pass all eight and still solve a problem nobody has. The gates are a quality floor, not a product strategy.

Why the boundary matters

description is the only thing a host sees before loading a skill. If it only says what the skill does, the host has to load it in every superficially similar situation. A skill that should not have fired does not usually error — it does something plausible, reports success, and you find out later.

We scanned 275 installed skills across four host directories. 15 of them declare a negative trigger. The script that produced this number is in the repository as scripts/survey_triggers.py — run it on your own machine and the number will move.
