Agent Skills

Most agent skills never say when not to use them

Agent skills are a new format with an old failure mode: the instructions are fine, the boundary is wrong.

I scanned 275 installed skills. 15 declare a boundary.  ·  Code and data  ·  中文版

Short version: a skill's description is the only text a host reads before deciding whether to load it. If the description never says when the skill should not fire, the host loads it anyway. I scanned 275 installed skills; 15 carry that sentence. This post is about the missing 94.5%.

I wanted to check how common this is, so I wrote a script that walks every SKILL.md installed under the usual host directories (.claude, .agents, .cursor, .codex), parses the frontmatter, and looks for any negative trigger in the description field — Do not use, Not for, Avoid using, Not intended for.

SKILL.md files found:        374
unique skills:               275
with frontmatter description: 275
contain a negative trigger:   15
do not:                       260
negative-trigger rate:        5.5%

Why 374 files but 275 skills: the same skill is routinely installed into several host directories at once. Counting every copy would weight the result toward whatever the user installed most widely, so the script collapses on directory name first.

94.5% of skills never tell the host when to stay away.

The split by origin is the interesting part:

The curated pack is about 5x more disciplined than the long tail. It is still 79% missing. "Better than community" is a low bar when community is at 4.3%.

Sample caveat: 275 skills from one Windows machine, dominated by a handful of public collections (Anthropic's examples, the Azure pack, superpowers, gstack) plus scattered installs. Not a random sample, not a census. Rerun it on your machine and the number will move. A 21% vs 4% gap, though, is unlikely to be sampling noise.

Why the boundary matters more than the body

description is the only thing an agent sees before deciding whether to load a skill. It is a retrieval key, not a summary for humans.

If the description only says what the skill does, the agent has one option: load it in every superficially similar situation and let the body sort it out. That works when the skill's body is defensive. It fails when the skill is eager — and most skills are eager, because people write them to be helpful.

The failure is quiet. A skill that shouldn't have fired doesn't usually error. It does something plausible, reports success, and you find out later.

Here is a real negative trigger from sync-skill-mirror, a skill that mirrors a canonical skill directory into a published copy:

User saysExpected
"Publish the skill to skills.sh."does not activate

Why refuse? Because publishing and mirroring are different steps. If the skill fires here, the agent dutifully syncs the mirror, reports "done", and the user believes the release happened. Nothing errored. The wrong work was completed.

That class of mistake is more expensive than a refusal, because a refusal at least stops you.

What the skill actually looks like

The workflow is unglamorous: one repository keeps the same skill in two places.

plugins/<name>/skills/<skill>/   ← canonical, edited here
skills/<skill>/                  ← mirror, read by skills.sh and manual installs

Edit the first, forget the second, and everyone who installed gets a stale copy with no warning. I wanted this to stop being something anyone has to remember.

The skill is 103 lines, ~890 tokens. Five steps, each with a command and an exit condition:

python scripts/sync_mirror.py --check     # exit 0 in sync, 1 with a drift list
python scripts/sync_mirror.py             # mirror
python scripts/sync_mirror.py --check     # must print "mirror is in sync"

Every step is traceable to something that already exists: the exit codes come from the script's implementation, the "in sync" string comes from an actual run, the drift-list behavior was observed. If a step could not be traced to evidence, it did not go in.

That constraint is the whole method. The common failure when writing a skill is describing the workflow instead of harvesting it, which produces prose like "verify the sync succeeded" — a step the agent has to improvise at runtime.

Eight gates, scored 0/1/2

Before publishing I ran the skill through a scorecard. It is not a benchmark, it is a checklist that makes specific failures visible:

16/16. The two gates that caught real problems were both about triggering, not content.

The negative tests are the useful part:

UtteranceExpected
"Sync my fork with upstream."does not activate
"Copy this directory to another drive."does not activate
"Publish the skill to skills.sh."does not activate

Each one is a plausible thing a user would say in this repository, and all three should route elsewhere. Without them, "sync" and "mirror" pull in everything.

Four things you can copy

No tooling required:

  1. End your description with Do not use for ... and make the exclusion discriminating. "Not for unrelated tasks" excludes nothing.
  2. Write at least one negative trigger test — a sentence a user might realistically say that should not activate the skill. If you cannot think of one, the skill's scope is probably too broad.
  3. Give every step a machine-checkable done condition. Not "confirm the sync succeeded" but "--check prints mirror is in sync".
  4. Prefer numbers to adjectives. ~890 tokens beats "lightweight". exit code 1 beats "detect drift".

Questions this raises

What is an agent skill?

An agent skill is a directory whose SKILL.md file carries name and description in its frontmatter, plus optional references and scripts. Hosts such as Claude Code, Codex, and Cursor read the description first, decide whether it matches the conversation, and only then load the body.

What is a negative trigger in a skill description?

A negative trigger is a sentence in description that names when the skill should not fire: Do not use for ..., Not for ..., Avoid using ..., Not intended for .... It is the only routing signal a host sees before the body is read.

How do I stop a skill from activating when it should not?

Put the exclusion in description, not in the body. The host never reads the body when deciding whether to load, so a "do not use this for X" paragraph inside SKILL.md cannot prevent the load. Name the adjacent task and, where possible, the skill that should handle it instead.

How long should a skill description be?

Long enough to carry three things: what it does, when to use it, and when not to. The third part is the one usually missing, and it is the only part a host can use to route a request away.

What this does not prove

Eight gates and 5.5% say nothing about whether a skill is useful. A skill can score 16/16 and solve a problem nobody has. Boundary correctness is a quality floor, not a product strategy.

It is, however, the cheapest quality fix available: one sentence in description, and the agent stops doing the wrong work confidently.
